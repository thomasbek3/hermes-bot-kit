# Grokbot Override: parity with Hermes Bot Mode

Written before any override code, from the Bot Mode source
(`~/.hermes/hermes-agent/apps/desktop/src/plugins/hermes-bots/*`, Hermes commit `2bd378ed1b`).

**The rule this list enforces:** nothing Bot Mode can do is lost, and (owner decision, 2026-11-08) nothing
hands off to stock Bot Mode in normal use. The override never removes, disables or unregisters Bot Mode. It
hides the stock **Bots** tab with CSS while the override is on, and every capability below is one of

- **Implemented** in the override screen, on the same gateway calls and the same chat, or
- **Partial**: part implemented; the Notes say exactly which part is not, or
- **Fallback / Later**: not native yet (none remain after the v2 merge). Bot Mode is untouched, so any such
  capability stays one palette command away (**Grokbot Override: toggle** turns the stock surface back on
  instantly), or
- **Blocked (needs Hermes change)**: the gateway or SDK offers no way for a plugin to do it.

While the override is on it also hides Hermes's top tab strip and the sidebar's "BOTS" tab label with scoped CSS (the
header band stays as the window drag region beside the traffic lights; lower zones are untouched), and toggling the
override off or any Bot Mode peek brings them back at once (`src/core/stock.js` `hideTopStripCss`, test
`test/stock.test.mjs`). The same style, with the same lifetime, also hides the bottom status bar, makes the titlebar
icon clusters on both sides invisible and click-through (still mounted), hides native scrollbars in the roster's
sidebar zone, and turns Hermes's own sidebar | workspace sash hairline solid (`hideWindowChromeCss`).

Look pass 5 (display and control placement only): the roster, chat, composer and panel use the reference layout's
class names and CSS (`src/ui/styles-ref.ts`, adapted by `refCss()`: scoped to `[data-gbo-root]`, tokens renamed `--g-*`,
lengths / 0.896 for Hermes's zoom; glue in `src/ui/styles-adapt.ts`). The sidebar's top row is sidebar toggle (Hermes's
own `view.toggleSidebar` through `ctx.runAction`, drawn only when the host offers it; the chat header shows it while the
sidebar is collapsed), search and +; the roster filters moved into the search field. The chat header is the bot pill,
a details toggle while the panel is closed, and one Share pill whose menu holds "Open another chat beside this one".
Bubbles group by sender within five minutes (`src/core/groups.js`) with tail corners and hover times; message actions
float beside the message on hover (right of a bot message, left of yours; out of flow, so hovering never moves the
transcript or covers the next bubble). Tests: `test/look-pass5.test.mjs`, `test/look9-card-scroll.test.mjs`.

Look 9: the sidebar footer is a round initials avatar and the person's name, with a round **Hermes settings** button
at its right. The name is the only one the running app exposes to a plugin, the computer's OS account name
(`window.hermesDesktop.getMachineProfile().username`; no SDK store holds a user or account display name); without it
the footer says "You". The button runs Hermes's own `nav.settings` action through `ctx.runAction` (the handler of ⌘,,
the palette entry and the titlebar gear) and is drawn only when the host lists that action; no other footer buttons,
because no other action is real there. The bot count is the footer's tooltip. In the open chat a thin red **NEW** line
sits above the first bot message the user has not seen (and above that message's time line): the override keeps, per
bot, the time of the newest message that was on screen while the user was looking (window focused, chat open, at the
bottom; plugin storage `seenAt`), decides the line when the chat opens and keeps it while the chat stays open; it never
goes above the user's own messages and never appears for messages read on arrival (`src/core/newMarker.js`, test
`test/look9-footer-newline.test.mjs`). Core's unread store (the row dot, R16) keeps no message position, so the
position is kept here; both are cleared by the same open.

The chat | profile panel hairline is the override's own resizer: drag (panel 260-480 px, chat at least 360 px),
stored as `panelWidth` in the override's plugin storage, double-click resets to 360 px (`src/core/panelWidth.js`,
`test/panel-width.test.mjs`). Display and layout only; no behaviour, routing or data changes.

Chat look and cards (2026-11-09): bot bubbles are one flat fill (dark `#242424`, light `#F0F0F0`); the profile panel
has a **Model** row showing the bot's model that opens the model picker (C21). Bot Chats are desktop sessions:
`session.create` and `session.resume` send `source: 'desktop'` as stock Desktop does, so the bot is told markdown,
`MEDIA:` files and inline widgets render (a gateway that refuses the key gets the call once without it; a session
created before keeps its old source until it restarts). A clarify request is an inline choice card at the end of the
transcript (lettered rows, multi-select with **Answer**, several questions one page at a time, typed text as the free-text answer, a
settled card stays in place; C11). `::card{…}` and `::preview{…}` lines in the open chat are drawn live from the
bot's own session (`src/core/directives.js`, `src/ui/Directives.tsx`): `card.v1` files read by REST relative to the
session's working directory and re-read every 3 s until final, buttons and widget intents sent back as hidden user
turns, previews in a frame sandboxed like stock's plus a no-network CSP, a widget intent sent at once only right
after the user stepped into that frame (otherwise shown with Send / Dismiss), card rows showing their `send` text
when it differs from the label. Re-reads key by the bot's route, so the transcript does not jump
while scrolling past a card. The generic skill that teaches bots the card format is `skills/agent-cards/SKILL.md`
(installed on request by the kit's `install.sh`, `KIT_CARDS_SKILL=1`). Tests: `test/look-pass6.test.mjs`,
`test/cards7-*.test.mjs`, `test/cards8-live-card.test.mjs`, `test/look9-card-scroll.test.mjs`.

The one escape hatch left in normal flows is the global toggle. **Open in Hermes Bot Mode** appears only in
error states: a send whose delivery is unknown and that carried no submission id, a chat that could not be
opened, a route this Desktop cannot hold open, and a question the connected gateway cannot take an answer for.
Every hand-off (`host.openSession`) carries the bot's exact connection route; only the active gateway's own
profile goes by name, with `keepAllProfilesScope` so Hermes's profile never moves. A row whose route is not
known yet (a remote row still loading) is refused with a message, and the override's own gateway, REST,
warm and delete calls refuse it too, instead of asking this machine for a same-named profile (live
2026-11-09; `src/core/routing.js` `botRouteProblem` / `stockOpenTarget`, test
`test/live-remote-route.test.mjs`). The override stays off in Hermes's HUD window (`test/loader-hud.test.mjs`).
Rows marked **Implemented** are tested against fakes shaped from the Hermes sources, and the
`test/loader-*.test.mjs` suites load the built `plugin.js` exactly as Hermes's runtime loader does (shim
modules, production React, a DOM) and drive it like a user. No live sends or mutations were made in this
round, so none of the rows is live-qualified yet.

Because Bot Mode keeps running, its background work is unaffected by the override: the bot relay drain,
the canonical-chat hide sweep, the mention middleware and completions in other chats, the
`chat.empty` claim, the **New agent** palette command and the screen portal all stay registered. Its roster
pane's unread tracker pauses while the override is on screen; the override runs the same tracker (R16).

## Known limits (transcript feel: scrolling, keys, media)

- **Not checked in the live app.** Stick-to-bottom, jump to latest, Show earlier and media sizing are covered by
  jsdom tests with a modelled layout (`test/tighter-t1-scroll.test.mjs`, `test/tighter-t5-*.test.mjs`): native
  smooth-scroll timing, the browser's own scroll anchoring (`overflow-anchor: auto`) and how it combines with the
  manual restore, and dark-mode visuals still need a live look in Hermes.
- **Jump to latest** ends on the reader's wheel, touch, pointer press in the transcript, scroll keys or a drag of
  the overlay scrollbar thumb; anything else (an assistive-technology scroll, for example) is treated as the
  jump's own progress until it arrives or the 1.2 s limit settles it at the bottom.
- **Show earlier** restores by the messages that were visible (keyed by their React identity) before decorative
  rows; if none of the rows that were visible is on screen after the load, the position is left to the browser.
- **No-remount keys (T4)** apply to replacements the controller can identify: a send confirmed by its stored row
  (the last 256 confirmations are remembered) and the replies of that turn. A live reply without a confirmed or
  stored user message before it (a compression, a recovery after a gap, a snapshot reload) gets no carried key
  and is remounted once: a remount is preferred to another message's identity.
- **Media sizes (T5)**: an image already read and decoded is drawn at once in its final box; an image seen for the
  first time still shows the generic placeholder until it decodes, a remote image loads only on **Load**, and the
  video placeholder assumes 16:9. So first-load and non-16:9 media can still change height once.

## Known limits (notifications, drafts, contract)

- **Native notifications (C31), one reply in two tabs.** Each side tab's chat runs its own controller, so the same
  reply has a different live id in each tab. To notify once, a reply with the same bot, runtime and text seen by
  another tab within 15 s counts as the same reply. A genuinely new reply with the same text that only one tab
  still shows (for example after the main tab switched to another bot) inside that window is therefore not
  notified. Exact correlation needs a shared gateway turn or message id, which the event stream does not give
  every frame. Tracked; not fixed.
- **Native notifications, closed side tabs.** A side tab is registered with the notifier when it first renders.
  Nothing tells the plugin when that tab closes without changing `app.ts`, so its subscription and last chat
  state stay until the override is switched off (one entry per side tab opened in the app session). A closed tab
  receives no events, so it never notifies. Tracked; not fixed.
- **Native notifications are not live-checked yet.** Delivery, Hermes's *Plugin notifications* setting and
  throttling, and click-to-open are covered by unit and loader tests with a stub OS door only.
- **Drafts (T8).** Text only, in memory for the app session: a plugin reload or app restart discards them, files
  are never kept across a switch (a refused send's files come back only into the same composer; otherwise a note
  asks to attach them again), and only the 20 most recently written bots keep a draft.
- **Contract probes (T10)** show that a private selector, key or bridge call is still present, not that it still
  means the same thing after a Hermes update. The sidebar seam colours stay fixed light/dark values.

## Known limits (source links)

- **`slack://` source links open the channel, not the message.** Hermes Desktop's external opener admits
  only `http:`, `https:` and `mailto:` (`apps/shared/src/external-url.ts`), so `ctx.os.openExternal` refuses
  a `slack://channel?team=…&id=…&message=…` deep link and the click falls back to
  `https://app.slack.com/client/<team>/<channel>`, which hands off to the Slack app at the channel. No
  documented https URL addresses a message from a team id, channel id and ts alone, and the plugin does not
  guess a workspace or bypass the opener. Slack **https permalinks**
  (`https://<workspace>.slack.com/archives/<channel>/p<ts without the dot>`) open the exact message, and the
  agent-cards skill tells bots to use them. If a future Hermes opener admits `slack:`, the deep link is
  already tried first.

## Architecture notes

**Two panes, Bot Mode's own zones.** Bot Mode puts its roster in the sidebar zone (tab **BOTS**) and its
Bot Chat in the main zone. The override does the same:

- `grokbot-override:roster`, a sidebar pane docked as a tab in the same zone as `hermes-bots:pane`
  (`dock: { pane: 'hermes-bots:pane', pos: 'center' }`). It is the Grok-style roster.
- A main-zone workspace tab (`host.openWorkspace('grokbot-override')`) with the chat column and the
  profile panel on its right.

**Toggle (palette "Grokbot Override: toggle", persisted in plugin storage).** ON registers the two
panes, injects one `<style>` that hides `[data-tree-tab="hermes-bots:pane"]` (strip, rail and narrow
overlay) and switches a selected stock BOTS tab to the override tab once per selection change (the same
guard the retired `bot-sections` used for SESSIONS). OFF unregisters the panes, removes the style and reveals the
stock Bots pane: stock is back instantly. Fallback actions set a temporary "peek" that removes the hide
style until the override tab is shown again.

**Private Hermes internals: one guarded contract (T10).** Everything the override uses that has no SDK door is
listed, each with a read-only probe, in `src/core/contract.js`: the DOM anchors of the window chrome it hides
(`[data-tree-tab]`, `[data-narrow-overlay-tab]`, `[data-tree-group][data-window-top] > [data-panel-header]`,
`[data-zone-tabstrip]`, `[data-panel-page-header]`, `[data-vertical]`, `[data-active]`, `[data-window-drag-handle]`, `[data-titlebar-cluster]`, `footer[data-slot="statusbar"]`,
`[data-tree-group]`, `[data-sash-overlap]`, `.aui-md`), Bot Mode's roster query key `['hermes-bots','roster']` and
localStorage keys (`hermes.plugin.hermes-bots.{bot-meta-v2,activity-toasts,group-chats}`), the desktop bridge
`window.hermesDesktop.{api,readFileDataUrl,getMachineProfile,requestMicrophoneAccess}` (`desktopBridge()` in
`src/ui/sdk.ts`), and every gateway event name the chat, reconnect and screen code acts on (including
`gateway.ready`, `session.replay_gap` and the `display.*` events, plus the `room.*` / `group*` families). A test
scans the source for event names and Hermes DOM attributes, so a new one that is not in the contract fails it. `core/stock.js` writes each chrome rule only
while its anchor is in the DOM, so a renamed anchor drops its rule instead of hiding the wrong thing. The
self-check writes the probe results as a `contract` block in `self-check.json`; a required entry that is missing
(the tab, top header, titlebar cluster and tree-group anchors, `window.hermesDesktop.api`) shows one quiet notice
per app session, once the override is on screen (probed 8 s after load, retried while it is not mounted yet, and
armed again when the override is switched on later). Optional entries (a status bar the user turned off, a closed
sidebar, Bot Mode data not written yet) report `absent`; events report `seen` / `unseen`. Any new private touch
point must be added to this list.

**Same engine, same chats.** Every RPC goes through a port of Bot Mode's `requestForBot`: a
source-scoped row uses `host.requestProfile(route, …)` with `profile` rewritten to the route's
`targetProfile`; an active-gateway row uses `host.request`. The chat is the `Bot Chat` registry row (C1).
History is shared both ways because it is the same stored session.

**Background polling, light on a struggling gateway (2026-11-16).** A remote gateway serves the Desktop's RPC
from a small thread pool; on a machine with multi-GB session stores the plugin's own polls could keep it saturated
and make the user's own "open this chat" time out. Every background poll now goes through
`src/core/backgroundPolls.js`, offered a turn on each 3 s tick and after each finished run (nothing is awaited
across polls, so a slow connection never holds another one's):

- **Lanes, one per connection.** The roster read, the source re-list, the room list and the idle refresh never run at
  once on one connection; a poll whose lanes are busy waits for a later tick. The union roster (`host.agents()`)
  reads `/api/profiles` from every registered non-SSH connection, also ones the plugin has not seen yet, and a plugin
  cannot list the registry: so that read is its own poll (every 60 s) that waits until no other background poll runs
  anywhere and holds every lane while it runs, except lanes known to be SSH sources (from the last union answer,
  roster rows and open chats; they answer from an inventory probe, not their gateway). Once it is due it holds a
  reservation: polls already running finish, no new one starts on a lane it needs until it has run, so busy
  connections cannot starve it (the reservation is dropped while the window is hidden). The active connection's rich
  `profiles.list` is a separate poll on that connection's lane only, so other connections never hold it up; each
  repaints the roster with the other's last answer.
- **Idle refresh is one pass per connection:** every open chat on it (main chat and extra tabs) has its tail re-read in
  turn every 15 s, starting after the last chat whose read was attempted and settled (applied, failed, or dropped
  past the deadline), so a chat that keeps timing out never holds the others back; a streaming chat skips only its
  own read. The chat
  controllers keep no idle timer of their own (`idleByHost`). Activity on the open chat (the unread/toast tracker's
  "refresh the open chat") marks that pass due once instead of reading directly; unread marks and toasts are still
  kept while the window is hidden.
- **Backoff and deadline.** Per connection and poll type the interval doubles after a run that failed or took more
  than 2 s (cap 5 min) and resets after a fast success. A roster read counts as failed when its union roster failed
  or a non-SSH source in it reported an error (what did answer is still painted). A run older than 30 s is backed
  off, lets the other poll types on its lanes go on, starts no further request (the roster read checks between
  `profiles.list` and `host.agents()` of a foreground read, a paged room list between pages, also stopping a
  background list when the window is hidden) and its late answer is dropped; the same poll
  on that connection is not started again until the old request settles, because a plugin cannot cancel a Desktop
  request: this relies on the Desktop's own transport timeouts (its REST bridge aborts a fetch after 30 s, gateway
  RPCs time out). Until then the other chats' idle reads on that connection wait too.
- **Hidden window.** Nothing starts while `document.hidden`, and a background roster read hidden between its two
  requests starts no union read. Both directions of `visibilitychange` are recorded, and the 3 s tick checks too (a
  missed event); on any hidden -> visible change, however short, every poll is due once whatever its backoff, the full
  roster read keeping its 60 s minimum since the last one.
- **Fresh answers only.** Own roster reads and source re-lists share one freshness order: a background answer is
  dropped once any later read started, and a foreground read (a write's re-read, Retry) is superseded only by a later
  foreground read. Room lists are numbered the same way. Switching the override off or stopping it retires every
  background run: no late answer is painted and no follow-up read starts (a run that was waiting for its first answer
  starts no second request), and a restarted plugin does not issue a read its stopped instance still has pending.
- **Foreground calls** (switch bot, open a chat and its `session.list`, send, a write's roster re-read, Retry,
  creating or disbanding a room, which re-lists rooms at once even while a background list is pending) never go
  through the lanes and are never delayed.

**Request shape:** the own roster read stays the full `profiles.list` (no params) plus `host.agents()`, at most once
per 60 s (was every ~15 s). The session fields are what the roster's previews, unread dots, activity toasts, the
"working" mark and the Bot Chat a click opens are made of (`canonical_session`, `last_session`, `worker_session`),
and the handler's only knob is the boolean `include_sessions` (no per-profile limit; it already reads only the Bot
Chat row and the newest session per profile, cached server-side until the store moves), so a light read would blank
those features: the session data is fetched less often rather than lighter. While Bot Mode's own snapshot is fresh
the override makes no `profiles.list` call at all, only the `host.agents()` re-list once per 60 s. Tests
`test/light-roster.test.mjs`.

**Read vs write.** Opening a bot that has a Bot Chat is reads only: roster cache, `session.list` (title lookup), REST message
tail, `cron.manage list`, `display.status`. Before attaching, a bot on a pooled connection gets one
route lease (keeps its socket open; no gateway state changes) held while its Chat tab shows it, and after the tab
closes only until an in-flight send or running turn settles (at most 30 minutes). The first write is
`session.resume` (attach, no new session) when the chat opens or the user sends; while a turn runs the screen also
reads `session.active_list`. Sends, stops, approvals, answers to questions, slash commands, edits,
reactions, room posts, cron toggles and every roster-side write (pin, hide, groups, profile edits, profile
config, create / duplicate / delete a bot, job create / edit / remove / run, screen start / takeover) happen
only on a user click, through the call stock Bot Mode (or the app's Cron page) makes for the same action;
creating a Bot Chat (C3) only on a roster click, **Start Bot Chat**, or right after the user creates a bot
(R13, with the intro).

**Code layout.** `src/core/*.js` is plain ESM with no imports from the app, so `node --test` runs it
without a build: routing, canonical lookup and creation, history normalisation, the event reducer,
delivery rules, approvals and other prompts, slash commands, mentions, media, tool detail, voice requests,
activity tracking, group rooms, roster merge and sections, roster view and filters, bot metadata,
attention, profile and cron operations, profile config, screen, usage, colours. `src/ui/*.tsx` is the React
UI; `src/ui/wiring.ts` connects the roster-side surfaces to the chat side (R13 kickoff → C3, R12 Open in new
tab → C26, **+ → New group chat…** → R14, room failures → R15). `build.mjs` bundles both with esbuild into
the committed single-file `plugin.js` (`react`, `react/jsx-runtime` and `@hermes/plugin-sdk` external, the
only imports the runtime loader allows; the kit's noVNC is bundled in, MPL-2.0, see NOTICE.md).
