# Grokbot Override: parity with Hermes Bot Mode

Written before any override code, from the Bot Mode source
(`~/.hermes/hermes-agent/apps/desktop/src/plugins/hermes-bots/*`, Hermes commit `2bd378ed1b`).

**The rule this list enforces:** nothing Bot Mode can do is lost, and (owner decision, 2026-11-08) nothing
hands off to stock Bot Mode in normal use. The override never removes, disables or unregisters Bot Mode. It
hides the stock **Bots** tab with CSS while the override is on, and every capability below is one of

- **Implemented** in the override screen, on the same gateway calls and the same chat, or
- **Partial**: part implemented; the Notes say exactly which part is not, or
- **Fallback / Later**: not native yet (none remain after the v2 merge). Bot Mode is untouched, so any such
  capability stays one palette command away (**Grokbot Override: toggle** turns the stock surface back on
  instantly), or
- **Blocked (needs Hermes change)**: the gateway or SDK offers no way for a plugin to do it.

While the override is on it also hides Hermes's top tab strip and the sidebar's "BOTS" tab label with scoped CSS (the
header band stays as the window drag region beside the traffic lights; lower zones are untouched), and toggling the
override off or any Bot Mode peek brings them back at once (`src/core/stock.js` `hideTopStripCss`, test
`test/stock.test.mjs`). The same style, with the same lifetime, also hides the bottom status bar, makes the titlebar
icon clusters on both sides invisible and click-through (still mounted), hides native scrollbars in the roster's
sidebar zone, and turns Hermes's own sidebar | workspace sash hairline solid (`hideWindowChromeCss`).

Look pass 5 (display and control placement only): the roster, chat, composer and panel use the reference layout's
class names and CSS (`src/ui/styles-ref.ts`, adapted by `refCss()`: scoped to `[data-gbo-root]`, tokens renamed `--g-*`,
lengths / 0.896 for Hermes's zoom; glue in `src/ui/styles-adapt.ts`). The sidebar's top row is sidebar toggle (Hermes's
own `view.toggleSidebar` through `ctx.runAction`, drawn only when the host offers it; the chat header shows it while the
sidebar is collapsed), search and +; the roster filters moved into the search field. The chat header is the bot pill,
a details toggle while the panel is closed, and one Share pill whose menu holds "Open another chat beside this one".
Bubbles group by sender within five minutes (`src/core/groups.js`) with tail corners and hover times; message actions
float beside the message on hover (right of a bot message, left of yours; out of flow, so hovering never moves the
transcript or covers the next bubble). Tests: `test/look-pass5.test.mjs`, `test/look9-card-scroll.test.mjs`.

Look 9: the sidebar footer is a round initials avatar and the person's name, with a round **Hermes settings** button
at its right. The name is the only one the running app exposes to a plugin, the computer's OS account name
(`window.hermesDesktop.getMachineProfile().username`; no SDK store holds a user or account display name); without it
the footer says "You". The button runs Hermes's own `nav.settings` action through `ctx.runAction` (the handler of ⌘,,
the palette entry and the titlebar gear) and is drawn only when the host lists that action; no other footer buttons,
because no other action is real there. The bot count is the footer's tooltip. In the open chat a thin red **NEW** line
sits above the first bot message the user has not seen (and above that message's time line): the override keeps, per
bot, the time of the newest message that was on screen while the user was looking (window focused, chat open, at the
bottom; plugin storage `seenAt`), decides the line when the chat opens and keeps it while the chat stays open; it never
goes above the user's own messages and never appears for messages read on arrival (`src/core/newMarker.js`, test
`test/look9-footer-newline.test.mjs`). Core's unread store (the row dot, R16) keeps no message position, so the
position is kept here; both are cleared by the same open.

The chat | profile panel hairline is the override's own resizer: drag (panel 260-480 px, chat at least 360 px),
stored as `panelWidth` in the override's plugin storage, double-click resets to 360 px (`src/core/panelWidth.js`,
`test/panel-width.test.mjs`). Display and layout only; no behaviour, routing or data changes.

Chat look and cards (2026-11-09): bot bubbles are one flat fill (dark `#242424`, light `#F0F0F0`); the profile panel
has a **Model** row showing the bot's model that opens the model picker (C21). Bot Chats are desktop sessions:
`session.create` and `session.resume` send `source: 'desktop'` as stock Desktop does, so the bot is told markdown,
`MEDIA:` files and inline widgets render (a gateway that refuses the key gets the call once without it; a session
created before keeps its old source until it restarts). A clarify request is an inline choice card at the end of the
transcript (lettered rows, multi-select and several questions with **Answer**, typed text as the free-text answer, a
settled card stays in place; C11). `::card{…}` and `::preview{…}` lines in the open chat are drawn live from the
bot's own session (`src/core/directives.js`, `src/ui/Directives.tsx`): `card.v1` files read by REST relative to the
session's working directory and re-read every 3 s until final, buttons and widget intents sent back as hidden user
turns, previews in a frame sandboxed like stock's plus a no-network CSP, a widget intent sent at once only right
after the user stepped into that frame (otherwise shown with Send / Dismiss), card rows showing their `send` text
when it differs from the label. Re-reads key by the bot's route, so the transcript does not jump
while scrolling past a card. The generic skill that teaches bots the card format is `skills/agent-cards/SKILL.md`
(installed on request by the kit's `install.sh`, `KIT_CARDS_SKILL=1`). Tests: `test/look-pass6.test.mjs`,
`test/cards7-*.test.mjs`, `test/cards8-live-card.test.mjs`, `test/look9-card-scroll.test.mjs`.

The one escape hatch left in normal flows is the global toggle. **Open in Hermes Bot Mode** appears only in
error states: a send whose delivery is unknown and that carried no submission id, a chat that could not be
opened, a route this Desktop cannot hold open, and a question the connected gateway cannot take an answer for.
Every hand-off (`host.openSession`) carries the bot's exact connection route; only the active gateway's own
profile goes by name, with `keepAllProfilesScope` so Hermes's profile never moves. A row whose route is not
known yet (a remote row still loading) is refused with a message, and the override's own gateway, REST,
warm and delete calls refuse it too, instead of asking this machine for a same-named profile (live
2026-11-09; `src/core/routing.js` `botRouteProblem` / `stockOpenTarget`, test
`test/live-remote-route.test.mjs`). The override stays off in Hermes's HUD window (`test/loader-hud.test.mjs`).
Rows marked **Implemented** are tested against fakes shaped from the Hermes sources, and the
`test/loader-*.test.mjs` suites load the built `plugin.js` exactly as Hermes's runtime loader does (shim
modules, production React, a DOM) and drive it like a user. No live sends or mutations were made in this
round, so none of the rows is live-qualified yet.

Because Bot Mode keeps running, its background work is unaffected by the override: the bot relay drain,
the canonical-chat hide sweep, the mention middleware and completions in other chats, the
`chat.empty` claim, the **New agent** palette command and the screen portal all stay registered. Its roster
pane's unread tracker pauses while the override is on screen; the override runs the same tracker (R16).

| C6 | Send (`prompt.submit` on the runtime session; re-resume once when the runtime was reaped) | `group-turns.ts` `submitGroupTurnPrompt`, app `use-prompt-actions` | Implemented | Attaches with `session.resume {session_id: <stored>, omit_messages: true, source: 'desktop'}` on the bot's route (`source` as stock Desktop sends it; an `invalid_params` refusal naming a key drops that key for good and retries once). **Route lease:** a bot on a pooled connection is held open with one lease (`host.retainProfile`; `host.retainProfileSocket` on an older desktop) taken before the first attach; without it the socket closes between calls and the gateway reaps the runtime. **Two panes, Bot Mode's own zones.** Bot Mode puts its roster in the sidebar zone (tab **BOTS**) and its
Bot Chat in the main zone. The override does the same:

- `grokbot-override:roster`, a sidebar pane docked as a tab in the same zone as `hermes-bots:pane`
  (`dock: { pane: 'hermes-bots:pane', pos: 'center' }`). It is the Grok-style roster.
- A main-zone workspace tab (`host.openWorkspace('grokbot-override')`) with the chat column and the
  profile panel on its right.

**Toggle (palette "Grokbot Override: toggle", persisted in plugin storage).** ON registers the two
panes, injects one `<style>` that hides `[data-tree-tab="hermes-bots:pane"]` (strip, rail and narrow
overlay) and switches a selected stock BOTS tab to the override tab once per selection change (the same
guard the retired `bot-sections` used for SESSIONS). OFF unregisters the panes, removes the style and reveals the
stock Bots pane: stock is back instantly. Fallback actions set a temporary "peek" that removes the hide
style until the override tab is shown again.

**Same engine, same chats.** Every RPC goes through a port of Bot Mode's `requestForBot`: a
source-scoped row uses `host.requestProfile(route, …)` with `profile` rewritten to the route's
`targetProfile`; an active-gateway row uses `host.request`. The chat is the `Bot Chat` registry row (C1).
History is shared both ways because it is the same stored session.

**Read vs write.** Opening a bot that has a Bot Chat is reads only: roster cache, `session.list` (title lookup), REST message
tail, `cron.manage list`, `display.status`. Before attaching, a bot on a pooled connection gets one
route lease (keeps its socket open; no gateway state changes) held while its Chat tab shows it, and after the tab
closes only until an in-flight send or running turn settles (at most 30 minutes). The first write is
`session.resume` (attach, no new session) when the chat opens or the user sends; while a turn runs the screen also
reads `session.active_list`. Sends, stops, approvals, answers to questions, slash commands, edits,
reactions, room posts, cron toggles and every roster-side write (pin, hide, groups, profile edits, profile
config, create / duplicate / delete a bot, job create / edit / remove / run, screen start / takeover) happen
only on a user click, through the call stock Bot Mode (or the app's Cron page) makes for the same action;
creating a Bot Chat (C3) only on a roster click, **Start Bot Chat**, or right after the user creates a bot
(R13, with the intro).

**Code layout.** `src/core/*.js` is plain ESM with no imports from the app, so `node --test` runs it
without a build: routing, canonical lookup and creation, history normalisation, the event reducer,
delivery rules, approvals and other prompts, slash commands, mentions, media, tool detail, voice requests,
activity tracking, group rooms, roster merge and sections, roster view and filters, bot metadata,
attention, profile and cron operations, profile config, screen, usage, colours. `src/ui/*.tsx` is the React
UI; `src/ui/wiring.ts` connects the roster-side surfaces to the chat side (R13 kickoff → C3, R12 Open in new
tab → C26, **+ → New group chat…** → R14, room failures → R15). `build.mjs` bundles both with esbuild into
the committed single-file `plugin.js` (`react`, `react/jsx-runtime` and `@hermes/plugin-sdk` external, the
only imports the runtime loader allows; the kit's noVNC is bundled in, MPL-2.0, see NOTICE.md).

**Tests.** `node --test test/*.test.mjs`. The `test/loader-*.test.mjs` suites share one harness:
`test/hermes-loader.mjs` (a replica of Hermes's runtime loader and SDK shims) and `test/loader-boot.mjs`
(jsdom, createRoot, a fake host; optional SDK dialog / menu parts from `test/fixtures/smoke-sdk.mjs`).
`loader-smoke.test.mjs` and `loader-smoke-legacy.test.mjs` render every surface of both parity sides with
and without the SDK parts; `loader-clickthrough.test.mjs` drives roster → chat → repeated bot switches →
profile → every dialog and checks nothing was written; `loader-wiring.test.mjs` covers the cross-side seams.
